# 控制面在谁手里？——用 Pi 理解并改造 Agent 的工作方式

> **控制面主线版｜75 分钟，含 10 分钟问答；附 60 / 90 分钟安排**  
> 资料基准：2026-10-09（Asia/Shanghai）；演示固定 Pi **1.1.0**，不临场跟随最新版本。  
> 听众：经常使用 AI 编程工具、熟悉研发流程，但不必使用过 Pi。  
> 核心命题：**不只问 Agent 能替我做什么，还要问我能否看清、干预并改造它的工作方式。**  
> 分享结果：带走评价 Agent 的五个问题，并选一个低风险控制点做试验；不是要求大家换工具或搭完整平台。

## 讲者先读：叙事、证据与本次取舍

全场只有一条主线：**四种失控 → 对应控制点与现场证据 → 从交互扩展到长跑 → 判断标准与试点。** 不再把“五个亮点”列成另一条并行主线，也不在最后重新演示一遍前面讲过的机制。

开场是讲者构造的情境，不是未经确认的亲历。对其他产品不做“全都封闭、不能分支、不能干预”的概括；把问题作为检查清单，让听众评价自己的工具。Pi 是可检查、可扩展的研究样本，不是唯一可能的答案。〔证据：[O02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o02)、[O08](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o08)〕

## 0｜00:00–04:00｜开场：同一条指令，为什么突然不一样了？

**画面 01：指令没变，结果变了。**

**讲稿**

先设想一个情境。你已经把“修 CI 失败”这件事做成了常用流程：给它任务，等它改代码，再检查结果。某一天，同样的指令，结果却和昨天不一样了。

这时候，我们很容易说一句：模型又抽风了。但你真要排查，会遇到几个更具体的问题：这轮到底带了哪些规则？工具列表有没有变化？它读到了哪一段历史？请求发给了哪个模型？

如果这些信息看不到，你只能继续改提示词试运气。**今天讨论的不是哪个模型更聪明，而是当工作流偏离预期时，我们手里有没有排查和改变它的办法。**

我把这类困扰分成四种：

1. 工作流变了，却说不清哪里变了。
2. 工具越接越多，每轮上下文也越来越重。
3. 想试另一种方案，讨论和工作状态却缠在一起。
4. Agent 已经跑歪了，却不知道什么时候能插进去一句有效的话。

**互动 20–30 秒**：请大家选一种最近遇到过的情况。不要求说用的是哪个品牌，先说卡住的地方。

我们用 Pi 作为研究样本，是因为可以沿着它的接口和实现，把这些问题拆成可观察的机制。但这些问题不是 Pi 专属的，也不意味着其他工具一定做不到。

我说的“控制面”，就是你能查看和改变工作方式的那些入口：输入怎样组成，工具怎样出现，指令怎样排队，历史怎样分支，以及进程结束后谁来续跑。拥有这些入口不等于模型一定答对，而是遇到问题时，你不只剩下“再试一次”。

**转场**：先用四分钟画清模型之外的那一层。接下来每遇到一种失控，我们就当场检查一种机制，不把演示攒到最后。

## 1｜04:00–08:00｜最小共同语言：模型之外，谁在组织工作？

**画面 02：一次请求背后的循环。**

```text
用户任务与规则
    ↓
Harness 组织本轮上下文、工具描述和模型请求
    ↓
模型生成文字或工具调用请求
    ↓
程序执行工具，把结果写入会话
    ↓
检查后续工具、排队输入与结束条件 → 必要时继续请求
```

**讲稿**

模型负责生成文本或提出调用请求；工具实际接触文件、程序和外部系统；Harness 把请求、执行、结果和会话组织起来。Pi 不是又训练出来的一个模型，而是这一层可扩展的运行程序。〔证据：[O02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o02)、[O12](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o12)〕

所以，“模型说已经运行测试”和“测试进程真的跑过”不是同一件事。后面我们尽量看第二种证据。

今天用一个小型任务统计仓库贯穿演示。规则很简单：只有明确标成 archived:true 的任务不计入，缺省字段也要计入。五条任务里，正确结果是四条。教材的初始实现误算成两条，人工准备的参考修复让五项测试全部通过。

**画面只展示已验证的结果，不现场等待模型修复**：故障结果 2/0/1/1，参考结果 4/1/1/2；分别对应总数、待办、进行中、已完成。告诉听众它是共同背景，不是本场模型生成记录。〔证据：[L01](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#l01)〕

围绕同一个仓库，我们要确认规则、检查测试、比较支线、关联任务数据，最后考虑把处理流程变成持续服务。场景会逐渐扩大，但每次都只问一个控制问题。

默认 read、bash、edit、write 是起点，不是 Pi 只能有四个工具。今天也不背包名和全部命令；先记住：**指导模型的文字，与控制运行过程的程序，不是同一种东西。**〔证据：[O03](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o03)〕

## 2｜08:00–20:00｜场景一：工作流变了，我能不能知道哪里变了？

### 08:00–11:00｜先列清模型看见了什么

**画面 03：不是“提示词一份”，而是输入来源清单。**

```text
本轮模型输入从哪里来？
基础指令 / 项目 AGENTS.md / 按需加载的 Skill
扩展增改的上下文 / 工具定义 / 活动历史 / 本轮选中的材料
实际模型与请求配置也需要一起记录
```

**讲稿**

回到开场：如果修 CI 的工作流突然变了，第一步不应该是把提示词加长，而是把输入来源列出来。是规则变了、工具变了、历史变了，还是模型与配置变了？

Pi 的上下文和扩展资源有可检查的入口。你自己的 AGENTS.md、Skill 和扩展可以纳入版本管理，扩展也支持重新加载。这给了我们比较变更的基础，但**能 diff 几个文件，不代表整个运行环境已经完全可复现**；模型、依赖和动态读取的数据仍要记录。〔证据：[O07](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o07)、[O08](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o08)、[O12](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o12)〕

例如，写进 AGENTS.md 的“不要修改测试”，首先是一条给模型的规则，不是文件系统权限。需要不可绕过的保护时，必须在实际执行和权限层落实。今天不会用一次看起来听话的回答，证明它永远遵守规则。

**可选画面，不冒充本机已彩排**：修改教学副本中的规则文件、在专用 Pi profile 中 `/reload`，检查后续行为。主场默认只展示规则 diff 和资源入口；真实 TUI 热更新须讲者另行彩排，不能在资料里标成已经通过。

### 11:00–15:00｜把反复提醒，变成明确执行入口

**画面 04：两种不同的约定。**

```text
自然语言：完成以后请跑测试，并如实报告。
执行入口：/verify → 固定测试进程 → 退出码和实际输出 → 记录到会话
```

**讲稿**

如果每个任务都要重新提醒测试路径和报告格式，我们可以写一个很小的扩展，把确定性的部分交给程序。这里的 `/verify` 是用户命令：运行指定测试，读取退出码与中止标记，再显示并记录结果。

它不是模型可以自行选择的工具，也不是 CI 门禁。它证明的是：工作流里的一段确定动作，可以不再依赖模型临时解释那句提醒。

**现场**：有已彩排的 TUI 就加载扩展执行；否则展示真实 loader + exec 的验证记录。故障副本为 `FAIL; exit=1`，参考修复副本为 `PASS; exit=0`。不要把接口执行记录说成刚才的界面操作。〔证据：[O08](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o08)、[L01](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#l01)〕

模板可以复用输入，Skill 可以复用方法和资料，Extension 可以接入命令、工具和事件。选哪一个，取决于你是在解释“怎么做”，还是需要程序“确定执行”。不必把每条说明都写成扩展。

### 15:00–18:00｜连模型选择，也可以是可检查的策略

**角标：真实路由回调；模型目录是预置数据；没有模型请求。**

```bash
npm run demo:router
```

**画面 05：四种输入，四个路由结果。**

```text
新请求 / high          → planner
工具后续 / previous    → planner
新请求 / low           → builder
失败重试 / failed      → builder
```

**讲稿**

Virtual Model 让选择的虚拟名称与实际请求目标分开。这里把路由策略写成我们自己的代码：新请求按档位选择，工具后续和重试保留原模型。第二步最重要：不是界面档位一变，就立即在当前任务里换模型。〔证据：[O19](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o19)〕

这个例子不是证明“规划用强模型、执行用便宜模型”一定更好。我们只检查四种输入会怎样选择。真实质量、缓存、延迟与费用，要另做任务评估。它的价值在于选择逻辑可见、可测、可修改，而不是自动省钱。

### 18:00–20:00｜收回到第一个判断标准

**互动**：你目前工作流里，有没有一句反复提醒的话值得变成确定动作？有没有一条规则其实只需要写清楚，而不值得开发功能？

**讲稿**

开场的工作流漂移，并不会因为换成 Pi 就自动消失。区别是我们现在能把问题拆到输入、规则、执行入口和模型选择，知道该查看什么、改哪里。

**判断标准一：本轮看到了什么、哪些行为由谁决定，我能不能列清并检查？**

**转场**：规则能看清以后，下一种失控来自能力增长。工具接得越多，是不是每一轮模型都必须背着所有说明书？

## 3｜20:00–32:00｜场景二：工具很多，为什么每轮上下文也必须很多？

### 20:00–23:00｜先区分“接得进来”和“每轮看得见”

**画面 06：公司有 40 个工具，不代表每个任务需要 40 份完整描述。**

**讲稿**

设想你接入了一批内部工具。改一个筛选条件，可能只需要读文件和跑测试；做变更审查时，才需要任务系统、检查系统和其他记录。工具目录可以很大，但当前请求要用到的描述和结果未必都很大。

Pi 的设计演进提供了一个值得研究的例子：早期对 MCP 的态度，与后来通过 Codemode、按需暴露来接入工具，并不是简单的“支持或不支持”。本场只用一分钟讲这个变化，重点是装载方式而不是版本新闻。固定基线已内建 MCP / Codemode，不沿用早期文章的功能清单。〔证据：[O10](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o10)、[O14](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o14)〕

MCP 解决工具如何接入；direct、deferred 等设置涉及工具怎样暴露；Codemode 则让一段程序调用工具并处理结果。这些不是同义词，也不能把工具从 prompt 中隐藏等同于取消访问权限。

### 23:00–28:00｜现场：两份原始数据，只返回本次需要的交集

**角标：真实官方 QuickJS 与宿主工具；教学数据、手写脚本；无 MCP 连接、无模型生成。**

```bash
npm run demo:codemode
```

**画面 07：这次审查究竟需要什么？**

```text
任务工具：编号、状态、归档标记、描述、负责人、备注……
检查工具：编号、最近结果、原因、完整日志……
问题：只列出未归档、未完成且最近检查失败的任务编号与一句原因。

并行读取 → 按编号关联 → 过滤 → 返回 { id, reason }
```

**讲稿**

先不看代码漂不漂亮。看两次工具读取是否真的发生，最终有没有把邮箱、内部备注和长日志一起带出来。正确结果只有 T-101 和一句原因。

再看一个错误反例：故意漏掉“未完成”条件，已经完成的 T-103 就混进来了。程序成功运行不等于业务正确；明确的条件和反例，才让输出边界可以检查。〔证据：[L02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#l02)〕

这里的代码是讲者准备的。真实模型是否会写对，是另一项测试；这段演示验证的是运行时调用与筛选机制。两个独立读取可以重叠，前后依赖的动作不能因为想并行就放在一起。

**27:00 为运行排障硬截止**：出错就展示准备阶段报告，留足时间解释结果，不占用后续场景。

### 28:00–30:00｜它与“请只回答三句话”有什么不同？

**讲稿**

要求模型少回答一点，可能只是减少最后的输出；此前原始材料已经进入上下文。这里是在工具编排程序中先选择和聚合，再把选定内容交给后续推理。

所以我们控制的不只是答案长度，而是哪些工具结果进入下一轮。但字符变少不能直接换算成 token 或费用节省百分比，实际效果还受工具描述、请求次数、模型和缓存影响。本场不引用脱离测量条件的节省数字。

### 30:00–32:00｜少返回数据，不等于没有外部权限

**画面 08：两个不能混同的边界。**

- QuickJS 中直接调用 `process.cwd()` 会失败；它仍能通过注册工具接触宿主能力。
- 宿主计数器已经加一，脚本随后抛错，计数器不会自动退回零。

**讲稿**

第二个例子只是内存计数器，不是发真实通知。但它已经说明一个重要问题：脚本失败，不代表之前的动作从未发生。访问权限与返回数据范围要分别设计。〔证据：[O11](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o11)、[L02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#l02)〕

**判断标准二：工具从哪里来，本轮暴露哪些能力，又把哪些结果交给模型，我能不能控制？**

**转场**：工具结果可以筛选，历史讨论呢？如果想试另一条路线，能不能不把两套方案全塞在一起？

## 4｜32:00–40:00｜场景三：想试另一条路，为什么主线也变乱了？

### 32:00–34:00｜问题不只是聊天太长，而是不同问题缠在一起

**画面 09：同一个起点，两个不同问题。**

```text
共同目标：修复任务统计
├─ 主线：最小修改 → 运行五项测试
└─ 支线：将来要不要接受 archived:null？
```

**讲稿**

我们正在修缺省字段的处理，有人提出将来要不要接受 null。这个问题值得讨论，但它不应该悄悄变成本次修复的新需求。继续在同一段历史里聊，模型每一轮都要重新判断哪些是本次目标，哪些只是未来讨论。

会话分支给了我们另一种组织方式：共享共同起点，分别讨论，只把需要的结论带回。Pi 用树状会话组织记录，当前请求按活动路径构建上下文；`/tree` 的导航与 `/fork` 新建会话也不是同一个动作。〔证据：[O04](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o04)〕

### 34:00–38:00｜现场：不是只画树，而是看实际消息数组

**角标：真实 SessionManager；消息和摘要由讲者预置；不是 TUI 录像或自动摘要评测。**

```bash
npm run demo:sessions
```

**观察三步**：

1. 主线包含“最小修复、五项测试”，不包含兄弟支线的 null 讨论。
2. 支线保留共同目标，但带有自己的问题。
3. 加入显式摘要后，主线得到必要结论，而不是支线所有原文。

**讲稿**

这就是把上下文当成可以组织和检查的数据，而不只是界面里的一串消息。分支解决的是讨论路径，摘要解决的是带回什么。

摘要仍然可能丢约束、丢证据。原始记录存在，不等于后续模型每轮完整读取它。这里的摘要是手写的，不能借此声称自动摘要质量很好。〔证据：[O04](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o04)、[L02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#l02)〕

### 38:00–40:00｜最容易误会的地方：树不是文件快照

**讲稿**

请看最后一个观察：程序改过一份临时文件，然后导航到另一段历史，文件并没有倒回去。

**会话分支不是 Git 分支，更不是文件、数据库和外部通知的联合快照。** 要并行改代码，还需要工作目录与冲突处理；仅仅把聊天分开是不够的。

**互动**：主线修当前 bug，支线研究未来接口。需要带回主线的是所有讨论，还是“这次不改接口”的结论及理由？让一位听众回答。

**判断标准三：试错能否分支，结论怎样带回，哪些外部状态不会一起回退？**

**转场**：分支让我们能换路线。但是它正在走错的那一刻，新指令究竟什么时候会被收到？

## 5｜40:00–48:00｜场景四：跑歪以后，我什么时候能插进去一句话？

### 40:00–42:00｜先区分纠偏、追加任务和取消

**画面 10：三个动作，不是一个“停止”按钮。**

```text
Steering：把纠偏消息排进循环，在当前 turn / 工具批次完成后介入。
Follow-up：等当前工作没有更多工具或 steering 待处理时，再处理后续任务。
取消 / abort：另一条控制路径，不等于排入 steering，也不自动撤销副作用。
```

**讲稿**

设想它正在改多个文件，你发现方向不对，于是输入“后面改为只读检查”。我们必须问：这句话什么时候进入下一次请求？当前工具会不会停？同一批已经提出的其他调用呢？

**本场固定 Pi 1.1.0：Steering 不是即时截断。当前 turn 及工具批次完成后，循环才读取这类排队消息。** 不沿用“当前工具结束就跳过剩余工具”的宽泛描述。我们用固定源码和本地时序验证这个边界。〔证据：[O05](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o05)、[L03](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#l03)〕

### 42:00–46:00｜现场：排队顺序不等于生效顺序

**角标：真实 core loop 与队列；官方测试 provider 的预置响应；无真实模型、无 TUI、无文件修改。**

```bash
npm run demo:steering
```

**画面 11：只看顺序，先不展开全部 JSON。**

```text
请求 1 提出工具 A、B
A 运行中：先排入 Follow-up，再排入 Steering
A、B 都结束 → turn 1 结束
Steering 进入请求 2 → 教学工具 C 执行 → 当前工作收尾
Follow-up 进入请求 4 → 后续任务结束
```

**讲稿**

先看第一处：消息确实在工具 A 还没结束时排入，但没有撤销 A，也没有跳过 B。

再看第二处：Follow-up 更早排入，却更晚进入请求。因为这两个队列解决不同问题：纠偏尽早在约定边界介入，追加任务等待当前工作收尾，不是简单按打字先后混在一起。

程序分别检查顺序执行和并行工具批次。两种情况下都验证 A、B 完成后才交付 Steering；并行时不要求 A 比 B 先结束。看 `requests` 字段，还能确认第二次请求已包含纠偏输入，但没有提前包含 Follow-up。〔证据：[L03](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#l03)〕

这里后续工具 C 和所有回答都由教材预先指定，所以它**不证明真实模型一定听懂并遵守“只读”**。我们验证的是指令被交付到哪个位置，这与模型如何理解它是两层问题。

**45:00 为排障硬截止**：使用已验证 trace 继续，不临场接真实模型来“补证明”。

### 46:00–48:00｜哪些场景不能只靠一句纠偏？

**互动**：如果一个工具已经发出了通知，你现在输入“别发了”，能否认为通知被撤回？

**讲稿**

不能。队列给了我们明确的介入时机，不给我们时间倒流。对危险动作，要在执行前设计确认与权限；对已经发生的动作，要核对结果，必要时补偿。需要取消时也要检查实际工具如何响应取消，而不能只看 UI 停止转圈。

**判断标准四：新指令在哪个边界进入循环，它是纠偏、追加还是取消，分别不能保证什么？**

四种失控讲到这里，我们已经能检查输入、工具、历史和介入时机。最后扩展一个问题：如果你不在终端前，甚至原来的进程已经没了，谁负责继续？

## 6｜48:00–59:00｜从交互到长跑：分工与恢复不是同一个问题

### 48:00–50:00｜Subagent：只讲它解决的那一个问题

**画面 12：两个审查问题，两份结果契约。**

```text
父任务：判断统计修复是否值得提交审查
├─ 规则审查者：输入规则与实现，返回发现 / 依据 / 未验证项
└─ 测试审查者：输入测试与样例，返回发现 / 依据 / 未验证项
```

**讲稿**

如果要分工，可以让不同执行实例拿到各自需要的输入和工具，再把结构化结论交回。关键是边界清楚，不是多开几个窗口。

Pi 终端没有一套固定的内置 Subagent 工作流；可以用官方扩展示例，也可以通过 SDK 或子进程组织。本项目保留了真实双进程与 SDK 的演示，但今天不把它升级成第六个主主题。〔证据：[O20](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o20)〕

先记两条：上下文隔开不等于磁盘、账号和网络隔离；一名审查者失败，不能汇总成两项都通过。边界高度耦合时，单 Agent 可能更简单。完整演示留在 90 分钟版的加时或课后。〔证据：[O13](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o13)、[L02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#l02)〕

**转场**：这是“怎么分工”。即使只用一个执行实例，进程仍可能死亡；恢复是另一个维度的问题。

### 50:00–52:00｜Durable：人在终端前，和服务长期运行，是两种约束

**画面 13：从临时助手到持续服务。**

```text
阶段 A：读取任务，整理待审查列表
阶段 B：生成下一步处理结果
阶段 C：通知外部系统

B 运行一半，进程没了，重启从哪里继续？
C 已经发生，但完成记录还没保存，又该怎么办？
```

**讲稿**

人在终端前，可以看输出、检查文件、决定是否继续。但变成长跑服务以后，进程退出、容器重启、人员离开，都会成为正常情形。保存聊天记录还不够，我们需要可恢复的任务状态。

Pi Durable 是面向这类应用的独立实验性框架，不是普通终端 Pi 自动附带的恢复保证，也不是开启 Subagent 后自然获得的能力。本场固定版本，API 仍可能变化。〔证据：[O15](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o15)、[O21](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o21)〕

### 52:00–56:00｜现场：用执行次数检查恢复，而不是只看“成功”

**角标：真实官方 Harness、JSONL 存储、SIGKILL 与新进程恢复；无模型、无外部通知。**

```bash
npm run demo:durable
```

**展示顺序**：存储位置 → 第一个进程完成 A 并进入 B → 教材子进程中断 → 新进程重开同一存储 → 检查计数和结果。

```text
A 进入 1 次
B 进入 2 次
恢复阶段：B
最终待审查编号：T-101、T-102
```

**讲稿**

这次不是同一进程里重新调用一次函数，也不是讲者自己读一个 JSON 文件假装恢复。持久化和调度来自官方框架，观察计数器帮助我们看清哪些阶段重新进入。

这里的 T-101、T-102 是待审查列表，不是前面 Codemode 的“检查失败交集”；两个演示问的问题不同。A 没有重复进入，未完成的 B 重新进入，这是我们设置的中断位置得到的证据。它不代表任意动作都只执行一次。〔证据：[L02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#l02)〕

**55:00 为排障硬截止**：转到三次进程记录，继续讲故障窗口，不拿调环境替代恢复边界。

### 56:00–59:00｜最重要的反例：通知已经发出，但本地还不知道

**画面 14：这是故障推演，不是本次实跑通知实验。**

```text
调用意图已经保存
→ 外部服务接受通知
→ 进程中断，完成结果未保存
```

**讲稿**

恢复后，本地没看到完成记录，并不能证明外部服务没收到。盲目重跑可能重复发送，直接跳过又可能漏发。这是状态恢复与外部副作用之间的边界。

官方工具恢复规则区分是否允许安全重放；默认 unsafe。声明 safe 是开发者承担的语义承诺，不是框架替你证明幂等。我们刚才跑的是自定义阶段任务，不冒充内置 ToolTask safe/unsafe 分支测试。〔证据：[O17](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o17)、[L02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#l02)〕

同样，`requestId` 在同一 conversation 内对提交去重，不等于通知、付款或部署等外部动作端到端 exactly-once。外部系统需要可核对结果、稳定操作 ID 或合适的幂等设计；无法确认时，应保留不确定性，而不是编一个“恢复成功”。〔证据：[O16](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o16)、[O18](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o18)〕

**判断标准五：进程没了，谁保存工作状态，谁决定重跑，谁核对已经发生的外部动作？** 普通短任务不必因此升级架构；只有遇到长跑与恢复约束时，再评估这条路径。

## 7｜59:00–63:00｜自由越多，哪些责任越不能交给一句“可控”？

**画面 15：能改，不等于不用负责。**

```text
工作流规则          ≠ 不可绕过的权限边界
独立会话 / 子进程   ≠ 文件、账号和网络隔离
持久状态与恢复      ≠ 所有外部副作用 exactly-once
```

**讲稿**

我们今天看了很多可以检查和修改的地方。现在反过来问：这些入口由谁维护？扩展谁审阅？版本更新以后谁做回归？路由变复杂以后，收益是否大于成本？

Pi 的扩展在进程里运行。项目信任控制资源加载，不是操作系统沙箱；工作目录也不是自动的访问边界。解释器限制、会话隔离和任务恢复各自解决具体问题，不能相互借用保证。〔证据：[O13](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o13)〕

“控制面在你手里”不意味着所有策略都要自己开发。如果现成工具已经满足需要，继续用它可能更合适。只有当你反复遇到具体限制，且愿意承担实现、验证和维护，开放接口才转化成真正的价值。

社区实践值得借鉴的也是这种取舍：例如先把稳定能力做成 CLI，再接一层薄扩展；或者先在运行环境层缩小误操作影响。它们是作者的经验，不是所有团队都必须安装的标准答案。〔证据：[C03](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#c03)、[C04](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#c04)〕

**互动 30 秒**：如果只能解决一个问题，你优先要更长提示词、一个确定执行入口，还是更小的实际权限？让回答落到具体任务，不讨论抽象的“全自动”。

最后提醒：我们没有竞品基准，没有真实模型质量对照，也没有证明 Pi 在所有场景更快、更便宜。本场给的是检查方法、机制证据和采用条件，不是产品排行榜。

## 8｜63:00–65:00｜结束：带走一把尺子，再做一个小实验

**画面 16：换任何 Agent，都可以问这五件事。**

| 判断问题 | 今天对应的证据 |
|---|---|
| 本轮模型看到了什么，行为由谁决定？ | 输入来源清单、执行入口与模型路由 |
| 工具从哪里来，本轮暴露和返回什么？ | MCP / 按需暴露的解释，Codemode 调用与筛选 |
| 历史如何分支，哪些状态不会跟着回退？ | 活动路径、显式摘要、文件不回滚 |
| 新指令在哪个边界进入循环？ | Steering / Follow-up 的真实队列时序 |
| 进程没了，谁续跑、谁处理不确定结果？ | checkpoint、执行次数与外部副作用反例 |

**讲稿**

Pi 只是让我们把这些机制展开检查的一个样本。今天希望你带走的不是“以后都换成 Pi”，而是一把尺子：遇到一个 Agent，能问清它的工作方式，而不只看一次成功演示。

再给自己一个很小的课后动作：挑一个经常卡住、验收明确的低风险任务，先记录普通流程，再只改变一个控制点。比如工具结果先筛选，或者把重复验证做成确定入口。比较返工、人工审查时间和新增维护成本，不先造完整平台。

**收尾一句**：真正值得掌握的，不只是让 Agent 替你做事，而是出了问题以后，你知道它为什么这样做、能在哪里改变它。

## 9｜65:00–75:00｜问答：拿真实约束来，而不是问哪个品牌最好

优先问：输入来自哪里、谁能改文件、指令在哪个时机生效、哪些动作不能重复、什么证据能判断成功。未知版本、价格与未经验证的工具，不现场猜。

4. 会话分支、Subagent、Durable 分别解决哪一层问题？
