## 0｜00:00–04:00｜先问：你到底能改这个 Agent 的什么？

**画面 01：三个需求，不先放产品介绍。**

```text
我想规划时用一种模型，进入执行后按自己的规则选择模型。
我想让两个审查者只拿到各自需要的上下文，而不是共享全部聊天。
我想一次读取多份工具数据，只把真正需要的结果交给模型。
```

**讲稿**

大家好。今天我们研究 Pi，不是为了再看一次“AI 写了一个函数”。这件事大家已经很熟悉了。

我想从三个更接近工程团队的问题开始：如果你不满意一个 agent 现有的工作方式，你到底能改它的什么？只能改输入的提示词，还是可以改它如何选择模型、如何组织上下文、如何调用工具，以及如何接入你的系统？

先看屏幕上的三个需求。它们不是要求模型再聪明一点，而是要求运行它的程序按我们的设计组织工作。

请大家想一下：这三件事里面，哪一件最接近你们现在遇到的限制？

**停顿 20–30 秒，收一两条真实需求。先不回答所有实现细节。**

今天的主线就是这个。Pi 的官方定位强调让它适应使用者的流程；它提供的不只是一个终端界面，也有可扩展的运行时和供程序调用的接口。我们会把这个定位拆成能观察的行为，而不是停在“极简、灵活、可扩展”这些形容词上。〔证据：[O02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o02)、[O08](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o08)、[O12](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o12)〕

这次准备了五个观察角度：运行时定制、上下文组织、Codemode 工具编排、Subagent 任务分工，以及 Durable 的持久恢复。

这里先打一个预防针。它们不是五个都自动打开的“终端内置按钮”，也不都属于同一个产品层。我们会明确哪些是内建机制，哪些需要扩展或自己的程序，哪些属于独立的实验性框架。

看完以后，大家应该能判断两件事：第一，Pi 是否解决了你真实遇到的可定制问题；第二，为了这种自由，你愿不愿意承担相应的实现、验证和维护成本。

**转场**

为了读懂后面的演示，我们先用六分钟建立最小共同语言，然后马上进入亮点。

## 1｜04:00–10:00｜基础够用即可：Agent 不是一个会说话的函数

**画面 02：模型、工具、运行时。**

```text
人给出任务
    ↓
Pi 组织本轮上下文与工具描述
    ↓
模型生成文字 / 工具调用请求
    ↓
工具真实执行 → 输出回到上下文 → 必要时继续下一轮
```

**讲稿**

模型负责生成文本或提出工具请求；工具负责实际接触环境；Pi 负责把上下文、调用、结果和会话组织起来。它不是又训练出来的一个大模型。〔证据：[O02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o02)〕

例如，模型生成“运行测试”的文字，与测试进程实际运行，是两件事。我们需要工具执行结果，才知道测试到底发生了什么。

今天的共同样例是一个本地任务统计 CLI。五条任务，只有明确标成 archived:true 的任务被排除。缺省字段也算未归档。规则很小，但能够让我们清楚看到输入、实现和证据。

**画面 03：先数数据，再看结果。**

| 任务 | 状态 | archived | 计入？ |
|---|---|---|---|
| T-101 | open | 缺省 | 是 |
| T-102 | in_progress | false | 是 |
| T-103 | done | 缺省 | 是 |
| T-104 | done | false | 是 |
| T-105 | done | true | 否 |

正确结果是四个任务：一个待办、一个进行中、两个已完成。初始实现只接受显式 false，所以算成两个。教材中已经准备了失败测试和参考修复。

**操作，控制在 90 秒内**

```bash
npm test
npm run demo
```

这里指进入新建的故障样例副本运行，不是在资料包根目录运行。观察四项通过、一项失败；对照参考修复后的五项通过，以及 2/0/1/1 变成 4/1/1/2。

**讲稿**

这段我们不等模型现场思考。参考修复是人工准备的，用来建立共同任务背景，不把它伪装成 AI 输出。完整的联网修复提示留在手册中，课后可以自己复现。

我们今天关心的更深一层是：这样一条工作流，哪些地方可以从“每次提醒”变成“由程序定义”？

先记三个名称。Prompt Template 复用一段输入；Skill 复用一类任务的方法与资料；Extension 把命令、工具、事件等运行时能力接进来。Package 则用来分发这些资源。这里不用背所有字段，只要记住指导模型和执行程序不是一回事。〔证据：[O06](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o06)、[O07](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o07)、[O08](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o08)、[O09](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o09)〕

最后，默认 read、bash、edit、write 只是当前配置的起点，不是“整个 Pi 只能有四个工具”。接下来，我们开始改变运行方式。〔证据：[O03](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o03)〕

## 2｜10:00–20:00｜亮点一：不是只改 Prompt，而是改运行时

### 10:00–13:00｜先把“请验证”变成一个明确入口

**画面 04：两种不同的约定。**

```text
自然语言约定：完成以后请跑测试，并如实报告。
可执行入口： /verify → 固定测试进程 → 退出码与实际输出 → 记录到会话
```

**讲稿**

我们已经知道什么算正确。接下来不希望每次都重新描述命令、路径和结果格式，就可以做一个很小的扩展。

本例 `/verify` 注册的是用户命令，运行指定测试，检查退出码与中止标记，把真实结果显示并记录。它不是模型自己可以选择调用的工具，也不是 CI 门禁。〔证据：[O08](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o08)〕

**操作**：按手册加载已审阅的扩展，运行 `/verify`；若不做 TUI，展示真实 loader + exec 的已验证结果，明确说这是接口运行而不是界面实测。

```text
故障副本：verify: FAIL; exit=1; stopped=false
修复副本：verify: PASS; exit=0; stopped=false
```

这一步不复杂，但能区分两件事：一种是希望模型记住某条规则；另一种是把确定性的动作交给程序。它体现了定制的入口，不是 Pi 全部扩展能力。

### 13:00–17:00｜再改“请求究竟发给哪个模型”

**画面 05：选择的虚拟模型与实际路由不是一个概念。**

```text
界面选择：workshop/auto
高思考档的新请求 → 配置的 planner 模型
同一轮工具后续   → 保持刚才的物理模型
低思考档的新请求 → 配置的 builder 模型
失败重试         → 本例保持失败请求原来的模型
```

**讲稿**

如果扩展只能多放一个按钮，它的意义还比较有限。更能体现可编程性的是：模型路由也可以成为我们自己的逻辑。

Pi 的 Virtual Model 允许把一个可选择的虚拟模型，映射到实际模型与思考等级；路由在每次请求前运行，可以根据请求状态设计策略。这不是训练一个新模型，也不等于把两个模型的能力自动融合。〔证据：[O19](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o19)〕

这里写了一个很小的路由扩展：新用户请求按所选档位选择 planner 或 builder；工具后续和重试保持原来的模型。这是教学策略，不是宣称“强模型规划、便宜模型执行”一定最省。

**运行**

```bash
npm run demo:router
```

**必须先说**：这段是路由回调测试，模型目录和模型描述是明确标注的 fixture；没有请求真实模型。它证明四种输入会选出什么，不证明切换后质量、延迟、费用或界面表现。

**预期输出顺序**

```text
user/high      → planner
continuation   → planner
user/low       → builder
retry          → builder
```

**讲稿**

请看第二步。虽然界面上的档位发生了变化，工具后续仍保持原模型。为什么？因为“每一步都换模型”并不自动是优点；缓存、思考签名和对话连续性都需要考虑。官方文档也提醒模型切换可能影响 prompt cache。〔证据：[O19](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o19)〕

生产选择应由真实任务结果和成本记录支持，而不是看到 planner/builder 两个名字就认定架构更先进。

### 17:00–20:00｜把亮点落到“你能控制哪些点”

**画面 06：扩展所处的位置。**

```text
输入与上下文 → 模型路由 → 工具调用 → 工具结果 → 会话与交互
     ↑             ↑          ↑           ↑            ↑
              可以在适当的扩展接口接入自己的逻辑
```

**讲稿**

除了命令和路由，Pi 的扩展还能注册工具、接入事件、处理上下文和工具结果、定制交互。关键不是所有接口都要用，而是你有机会在恰当的位置实现自己的流程。〔证据：[O08](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o08)〕

官方 Pi 1.0 展示过让 Pi 为自己编写路由扩展，再重新加载使用。这比“让它写一个业务函数”更贴近它的定位：agent 也可以帮助你改造运行 agent 的程序。我们今天给出的确定性测试，就是先把这个想法拆成能独立验证的一小块。〔证据：[O22](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o22)〕

我也不建议看到 hook 就把安全责任全塞进去。某个工具入口能被拦截，不代表进程的所有文件和网络访问都受到了 OS 级隔离。自定义代码是能力，同时也是你需要审阅和维护的代码。

**互动 30 秒**：请听众说出自己工作流里一个“重复的提醒”和一个“值得写成确定性动作”的例子。

**本段结论**：Pi 的亮点不是附带更多命令，而是让运行方式本身成为可改造的对象。下一步，我们改造的是模型拿到什么上下文。

## 3｜20:00–27:00｜亮点二：把上下文当作可以组织的数据

### 20:00–22:00｜同一个任务，为什么不把所有讨论都塞进去？

**画面 07：共同起点、两个问题。**

```text
共同目标：修复任务统计
├─ 主线：最小修改 → 运行五项测试
└─ 支线：将来要不要接受 archived:null？
```

**讲稿**

真正的研发任务很容易长出支线。修筛选条件的时候，有人讨论 null，有人讨论接口迁移，还有人开始讨论数据库设计。把这些都留在同一段模型上下文里，模型就要反复判断哪些还属于当前任务。

Pi 的会话结构是树。当前请求使用活动路径构建上下文；其他分支的原文不会因为存在于文件中，就自动全部进入当前路径。分支、导航和摘要给了我们组织讨论的机制。〔证据：[O04](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o04)〕

这里我们不只画一棵树，而是打印真正构建出来的上下文。

### 22:00–25:00｜运行真实会话 API，查看模型将拿到什么

```bash
npm run demo:sessions
```

**说明验证等级**：真实 Pi 1.1.0 `SessionManager`，消息与摘要由讲者预置，没有调用模型，也不是 TUI 的 `/tree` 录像。

**观察三个结果**

1. 主线上下文包含“最小修复、五项测试”，不含兄弟分支里的 null 讨论。
2. 支线上下文包含自己的问题，两个路径共享共同起点。
3. 显式带回手写摘要后，主线得到简短结论，而不是支线的所有原文。

**讲稿**

现在我们看到的不是“应该隔开”，而是实际生成的消息数组。把上下文当成可检查的数据，能帮助我们判断为什么某个任务拿到了无关材料，或者遗漏了关键约束。

这里的摘要是我写好的，所以不能借此证明模型自动摘要质量很好。真实使用中，摘要仍需保护目标、限制、证据和未完成项。

另外，程序还改了一份临时文件，然后做会话导航。文件内容没有随会话倒回。**会话树不等于 Git 分支，也不等于文件快照。** 这是一条必须现场指出的边界。

### 25:00–27:00｜何时值得使用，何时不值得

当你要做临时审查、研究一个工具或比较两个方案时，分支是有用的组织手段。Armin 的一手实践也用过这种方法。它不是保证效果的仪式；一个很短的任务，直接继续可能更简单。〔证据：[C02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#c02)〕

压缩解决的则是后续输入长度。原始记录还在，不意味着每一轮继续完整读取它。不要把“保存了历史”和“模型没有损失任何细节”混为一谈。〔证据：[O04](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o04)〕

**转场**：刚才我们控制哪些历史进入模型。接下来控制另一种输入：工具返回的大量原始数据。

## 4｜27:00–39:00｜亮点三：Codemode，把工具调用组织成一段程序

### 27:00–30:00｜先提出一个普通但具体的问题

**画面 08：两份输入，一份期望结果。**

```text
任务工具：任务编号、状态、描述、负责人、备注……
检查工具：任务编号、最近结果、原因、完整日志……
问题：只列出未归档、未完成且最近检查失败的任务编号与一句原因。
```

**讲稿**

假设我们要准备一次变更审查。任务系统能给出很多字段，测试系统也会给出长日志。但是这次的问题，只需要一个很小的交集。

一种办法是不断把原始结果塞给模型，再要求它自己关联和筛选。另一种办法是把“调用两个工具、按编号关联、过滤并返回少数字段”写成一段程序。

Codemode 就提供了这样的工具编排方式。它不是一个新的聊天模式，也不等于 MCP。MCP 解决工具如何接入；Codemode 关注用代码怎样调用和处理这些工具。当前基线有内建 MCP 与 Codemode，不沿用早期文章“没有 MCP”的功能清单。〔证据：[O10](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o10)、[O11](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o11)、[O14](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o14)〕

### 30:00–35:00｜运行程序，看工具边界与输出

```bash
npm run demo:codemode
```

演示材料明确列出实际使用的官方运行时、工具接入方式和检查项。**不是调用了两个本地函数，就自动宣称验证了 MCP 传输；不是预置了脚本，就宣称模型已经学会生成脚本。**

**画面 09：操作逻辑。展示实际演示文件中的代码，不手抄一个不同的伪 API。**

```text
同时请求 tasks 与 checks
→ 依据 taskId 关联
→ 过滤 archived:true、done 以及非失败检查
→ 显式返回 { id, reason }
```

**观察点**

- 两个工具是否真实被调用？调用的是哪两个？
- 输出有没有多带邮箱、内部备注和完整日志？
- 如果漏掉“未完成”条件，数据里会出现什么错误结果？
- 如果脚本不允许直接访问某个宿主能力，错误是什么？

**讲稿**

这段演示里的数据全部是教学数据。我们关心的是数据流发生了什么：程序确实调用工具，然后把输出压到这次问题所需的范围。

这里的并发不是魔法。两个读取任务没有依赖，所以可以组合；如果第二步必须用第一步返回的 ID，就不能简单把两者都塞进并行调用。

我也不会拿字符变少直接宣称 token 或费用节省百分之多少。可以观察输入输出大小，但真实 token、延迟和费用还受工具描述、额外调用、模型和缓存影响，需要另行测量。

### 35:00–37:00｜它与“让模型少说一点”有什么不同？

**讲稿**

要求模型“只给我摘要”，可能只是让它最后少写一些，但此前所有原始材料已经进入了模型上下文。这里的策略是：先在工具编排程序中选择和聚合，再把选定结果交给后续推理。

这不能替代权限管理。工具如果本来就能读很多数据，程序只是少返回一些，不等于从源头限制了读取权限。数据最小化和访问最小化，是两项相关但不同的工作。

因此，Codemode 的适合场景是有清楚结构的工具组合与数据处理，而不是把本来一句话就能做完的任务都改成脚本。

### 37:00–39:00｜解释器边界不等于外部工具没有权限

官方文档描述的 Codemode 解释器没有直接 Node、文件系统和网络 API，但可以通过注册工具接触外部能力。工具的副作用不会因为脚本后面报错就自动撤销。〔证据：[O11](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o11)〕

**互动 30 秒**：如果第一个工具已发出通知，第二个工具失败了，整个脚本报错是否意味着通知没发？

不是。这正是后面 Durable 段落要继续分析的问题。

**本段结论**：Codemode 的亮点是工具编排和结果边界可编程，不是无条件承诺更快、更安全。接下来再往上一层，不只组合工具，还组织不同 agent 的任务。

## 5｜39:00–50:00｜亮点四：Subagent，不是把所有人拉进同一个群聊

### 39:00–42:00｜先决定为什么拆，不先决定启动几个

**画面 10：变更审查中的两个独立问题。**

```text
父任务：判断这次统计修复是否值得提交审查
  ├─ 规则审查者：缺省 / false / true 的语义是否匹配？
  └─ 测试审查者：测试是否覆盖了本次故障与基本回归？

父任务只接收两份结构化结论，再决定下一步。
```

**讲稿**

如果把“修复、审查业务规则、审查测试、整理最终结论”都交给一个上下文，它也可能完成。Subagent 不是为了把这种简单任务必然变快，而是提供另一种组织方式：让不同任务获得相应的角色、输入和工具，再把结果交回协调者。

首先要澄清产品边界。终端 Pi 没有内建一种固定的 subagent 工作流；官方提供扩展示例，你也可以利用 SDK 或子进程构建。今天的示例是我们为讲解设计的组织方式，不冒充一个默认的 `/subagent` 内置命令。〔证据：[O02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o02)、[O20](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o20)〕

### 42:00–46:00｜看角色、上下文与结果，而不是只看两行“运行中”

```bash
npm run demo:subagents
```

**讲者先说明当前模式**：离线结构演示中，实际进程 / 会话机制与模型输出 fixture 必须分别标注；要看真实模型审查结果，使用手册中的联网命令，完成专用 profile 和模型准备后彩排。

**观察四件事**

1. 两个 worker 是否有各自的进程或会话标识？
2. 每个 worker 实际收到什么任务材料？有没有默认复制所有父对话？
3. 它们分别拥有哪些工具？是否需要写文件？
4. 父任务得到的是明确结论，还是两大段无法使用的原始日志？

**讲稿**

如果只是同时打印两行文字，不足以证明有两个独立 agent；如果用了预设响应，也不能声称模型已经独立审查正确。本段的离线模式只验证组织与传递机制，联网模式才观察真实模型行为。

在这个任务里，两位审查者都不需要修改代码，所以先给只读工具就够了。结果至少包含发现、依据和未验证项。父任务需要的是这份契约，而不是把所有过程原文重新塞回自己的上下文。

### 46:00–48:00｜为什么不能默认共享一切？

上下文隔开，能帮助角色聚焦，但不自动隔离磁盘、账号或网络。两个子进程如果共享同一可写目录，仍然可能互相踩文件。工具选择也不是操作系统安全边界。〔证据：[O13](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o13)、[O20](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o20)〕

如果任务是并行修改代码，就需要另外决定独立工作目录、冲突处理和最后集成方式。不要从“每个 agent 有自己的聊天”跳到“整个执行环境已经隔离”。

失败也要明示。一个审查者超时，不应该被汇总成“两项都通过”；父任务应看到哪项完成、哪项失败，哪些结论因此暂时不能下。

### 48:00–50:00｜可组合不等于越多越好

拆分增加了启动、输入准备、调用和汇总成本。任务高度依赖同一份隐含背景时，拆开可能比单 agent 更差。只有当边界清楚、输入能独立准备、返回结果能被使用时，分工才有意义。

**互动**：让听众判断“两个审查者”和“两个 agent 同时改同一个文件”，哪个更适合作为第一次试点，为什么。

**本段结论**：Subagent 的亮点是任务、上下文和结果契约可以由你组织，而不是“多开几个模型窗口”。接下来让这些工作在进程中断后仍有明确状态。

## 6｜50:00–60:00｜亮点五：Durable，让工作状态不只活在进程里

### 50:00–53:00｜一个会中断的流程

**画面 11：不要从 exactly-once 术语开始。**

```text
阶段 A：读取任务，整理待处理列表
阶段 B：生成下一步处理结果
阶段 C：通知外部系统

问题：B 运行途中进程停止，重启后从哪里继续？
更难的问题：C 已经发生，但“完成记录”还没落盘呢？
```

**讲稿**

之前我们主要考虑一个终端前的任务。如果它变成长期存在的服务，进程会退出，机器会重启，人会暂时离开。此时，不只需要保存一份聊天文本，还需要知道任务的状态、已完成的部分和可继续的部分。

Pi Durable 是面向这类应用的独立实验性框架，不是普通终端 Pi 自动附带的一层恢复保证。它的 API 仍可能变化，所以本场按固定版本准备，不把示例写法当成永久标准。〔证据：[O15](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o15)〕

### 53:00–57:00｜用中断前后执行次数验证恢复

```bash
npm run demo:durable
```

**展示顺序**

1. 指出实际使用的存储位置，以及为什么它在进程结束后还存在。
2. 第一个进程完成 A，开始 B；在受控位置中断。
3. 第二个进程重开同一存储并恢复调度。
4. 看 A、B 的执行次数和最终结果，而不是只看“恢复成功”四个字。

**讲者必须按报告表述**：演示究竟使用 Durable 的哪一层、哪些操作是真实的、是否有模型参与、是不是实际进程中断。不能用自己写的 JSON 断点文件冒充官方 Durable，也不能用同一进程中的普通重试冒充进程恢复。

**讲稿**

我们关注的是：已经持久化完成的部分有没有重复执行，尚未完成的部分按照什么规则继续。记录步骤的执行次数，就是为了让恢复行为能够被检查。

本次实际结果是 A 进入一次、B 进入两次；恢复后的待审查编号仍是 T-101 和 T-102。我们刚才验证的是自定义任务的阶段恢复，不是内置 ToolTask 的 safe/unsafe 分支。后面的通知例子是有来源的故障推演，不冒充已运行的外部通知实验。

这段无需一定有模型。先验证任务和存储机制，有助于把运行时问题与模型推理问题分开。以后再接真实模型，仍然需要测试它在恢复后的上下文里会怎么继续。

### 57:00–59:00｜最重要的反例：通知已经发出

**画面 12：故障窗口。**

```text
通知调用意图已保存
    ↓
外部服务接受通知
    ↓
进程中断，完成记录未保存
```

**讲稿**

恢复机制不能替你知道所有外部世界已经发生的事。对于这种结果不确定的动作，重新执行可能重复发通知，直接跳过也可能掩盖未送达。

官方工具恢复规则区分是否允许安全重放；默认 unsafe。针对调用意图已持久化后的中断，不能把所有操作无条件再执行一次。“safe”是开发者承担的语义承诺，不是框架替你证明幂等。〔证据：[O17](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o17)〕

同样，`requestId` 在同一 conversation 内对提交去重，也不等于任意外部通知只发生一次。本地事务与外部服务的副作用边界不同。〔证据：[O16](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o16)、[O18](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o18)〕

### 59:00–60:00｜什么时候值得用

如果你的需求只是修一个文件，不必为了名字里的 durable 升级架构。如果你要处理长运行、并发会话、可恢复任务或跨界面应用，它才值得进一步评估。

**本段结论**：亮点是把状态和恢复作为程序的一部分来设计，不是许诺“断了再连就什么都不会出错”。

## 7｜60:00–63:00｜自由度越高，哪些责任越不能省？

**画面 13：三个不能偷换的保证。**

```text
工作流规则       ≠ 不可绕过的安全边界
独立会话/子进程  ≠ 独立磁盘、账号与网络权限
持久状态/恢复    ≠ 所有外部副作用 exactly-once
```

**讲稿**

前面五个亮点有一个共同点：你能决定更多事情。但能决定，并不意味着不用负责。

扩展是运行在 Pi 进程里的代码。项目信任控制资源加载，不是整个进程的操作系统沙箱；工作目录也不是自动的访问边界。Codemode 的解释器限制、Subagent 的上下文隔离、Durable 的恢复机制，各自都有明确范围。〔证据：[O13](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o13)、[O11](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o11)〕

成本也要算完整：维护扩展、调试路由、准备子任务输入、汇总结果、处理版本变化，都可能抵消看起来节省的步骤。我们没有做竞品基准，也没有数据证明某种结构一定更快或更便宜。

社区里值得借鉴的是方法，而不是“必装清单”。例如把独立 CLI 作为稳定能力，再用薄扩展接入 Pi；或者在环境层缩小误操作影响范围。这些经验仍然需要结合团队权限和数据约束验证。〔证据：[C03](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#c03)、[C04](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#c04)〕

所以，Pi 是否适合你，关键问题不是“它有没有某个热门词”，而是你是否确实需要改造 agent 的运行方式，并愿意把这些改造当成工程软件来维护。

## 8｜63:00–65:00｜收束：五个亮点，回答的是一个问题

**画面 14：从使用产品，到定义工作方式。**

| 我们想控制什么 | 今天看到的机制 |
|---|---|
| 怎样执行、选哪个模型 | Extension / Virtual Model |
| 当前任务拿到哪些历史 | Session tree / branch / summary |
| 工具怎样组合、返回哪些数据 | Codemode |
| 工作怎样分给不同角色 | Subagent 的会话、工具和结果契约 |
| 进程中断后怎样继续 | Durable 的持久状态与恢复 |

**讲稿**

今天的重点不是记住五个名称，而是看到这五个控制点。

如果团队只是希望少一点配置、直接使用一个现成助手，Pi 的可定制性未必值得额外投入。如果你正在遇到特定的上下文、工具、路由或系统集成限制，这些接口才可能有真正的价值。

下周可以选一个低风险任务：写清输入、完成条件和不能做的事；先用普通流程做一次；再只改变一个控制点，记录收益和新增成本。不要一开始就搭完整多 agent 平台。

**收尾一句**：Pi 值得研究的，不只是“它能替我做什么”，而是“我能怎样把它改造成适合我们做事的程序”。
