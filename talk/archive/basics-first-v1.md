## 0｜00:00–05:00｜先看一个小错误，不从产品介绍开始

**画面 01：只放下面两行，不先解释产品。**

```text
业务同学数出来：未归档 4，待办 1，进行中 1，已完成 2
工具输出：      未归档 2，待办 0，进行中 1，已完成 1
```

**讲稿**

大家好。今天我们聊 Pi，但我想先不讲它是什么，也不放一页长长的能力清单。先看一个我们每天都可能碰到的小问题。

这里有一个任务统计工具。它读取一份 JSON，把未归档的任务按状态汇总。业务同学说有四个任务，工具却说只有两个。代码很短，问题不涉及复杂算法，甚至不需要联网。

现在把它交给一个 AI 编程助手。它很快给你一段补丁，然后回复：“问题已经修复，现在能够正确统计所有任务。”

我想请大家先想一个问题：**到这一步，你会直接合并吗？你还想看到什么？**

**停顿 20–30 秒，收两条回答。优先接住“测试”和“看看改了什么”，不展开模型好坏的争论。**

对，我们通常还想看失败是怎么复现的、改动是否符合原来的业务规则、测试到底有没有跑、最后的输出是什么。很多时候我们缺的不是一句更自信的解释，而是这些能被检查的证据。

这也是今天的切入点。我们当然关心模型能不能写对代码，但技术团队还需要解决另一个问题：**怎样让模型在我们的工作方式里做事，而不是每次重新交代一遍工作方式。**

比如，“先复现再修改”“不要偷偷降低测试要求”“修改以后一定跑验证”。第一次可以打在聊天框里，第二次可以复制，到了第十次，你会开始想：能不能把它变成项目规则？到了一个团队都这样做，你又会问：能不能变成一个入口，甚至接到已有的工程工具上？

今天用 Pi 来拆这件事。我们不试图证明某个模型比另一个聪明，也不要求大家听完立即换工具。我们只做三件事。

第一，看清一个编程 agent 从收到请求，到调用工具，再到拿到结果，中间发生了什么。第二，亲手走一遍有证据的修复。第三，把重复出现的一小段流程固化下来，并且知道这种固化的边界。

最后我们会用五分钟看 Pi Durable。不是再开一门框架课，而是看：当这件事从个人终端变成长期运行的应用时，为什么“重启后接着跑”远远不是全部问题。

先约定一个评价标准：**今天演示成功，不是模型说自己成功了，而是我们预先约定的检查通过了。**

**转场**

要理解后面这些操作，我们先用七分钟，把 Pi 放到正确的位置上。

**节奏提示**：开场讨论超过 1 分钟就收束；不在这里讲安装史、创始人故事或竞争产品列表。

## 1｜05:00–12:00｜模型、工具，以及把它们组织起来的 Pi

**画面 02：只画一张图。**

```text
人的任务 + 项目说明 + 当前会话
               │
               ▼
       Pi 组织本次模型输入
               │
               ▼
       模型返回文字或工具请求
          │               │
       最终回答        read / bash / edit / write
                          │
                          ▼
                     真实执行结果
                          │
                          └── 回到下一轮模型输入
```

**讲稿**

先把三个东西分开：模型、工具，以及组织它们工作的程序。

模型负责根据眼前的输入，生成文字，或者提出一个工具调用。例如，它可能提出“读这个文件”，也可能提出“执行这条测试命令”。工具是真正接触环境的那一层：读取文件、修改文件、启动一个进程。

Pi 在这里承担的是 agent 的运行与交互层。英文材料经常用 harness 这个词。今天我们可以直接把它理解成：**负责把任务、模型、工具、上下文和会话组织起来的程序。** 它本身不是又训练出来的一个大模型。〔证据：[O02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o02)〕

这个区分很重要。假设模型想执行 `npm test`，并不意味着它嘴里出现这两个单词，测试就真的运行了。要有工具执行请求，操作系统启动进程，再把标准输出、错误输出和执行结果返回。模型之后说“测试通过”，才有机会依据真实证据，而不是依据想象。

在我们的例子里，一次正常路径大概是这样：先读规则，再读代码，运行测试，看到断言失败，修改代码，再跑一次测试，最后组织回答。

注意，图里的循环是一个工作模型，不是对 Pi 内部所有细节的逐行复刻。一次请求可能涉及多轮模型和多个工具；过程中也可能失败、中断或者被人引导。关键不是背一段内部时序，而是知道：**工具结果会作为后续推理的输入，而不只是摆在屏幕上的附件。**〔证据：[O02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o02)〕

**画面 03：默认工具与实际证据。**

| 默认工具 | 在这个例子里做什么 | 你能观察到什么 |
|---|---|---|
| `read` | 读规则、源码、测试 | 模型实际看到了哪些内容 |
| `bash` | 运行测试与示例 CLI | 测试输出、退出结果 |
| `edit` | 有针对性地改动现有文件 | 原行为改成了什么 |
| `write` | 创建或写入文件 | 新增了什么文件或内容 |

默认启用这四个工具，不代表 Pi 总共只有四个工具。当前版本还有可选工具，也能通过扩展和 MCP 接入更多能力。这里我们刻意先不打开那些开关。能不能把一个小任务做得清楚，比一开始接多少服务更有价值。〔证据：[O03](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o03)、[O10](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o10)〕

那 Pi 对工程师最值得研究的是什么？不是“它也能读文件”，因为你熟悉的其他工具可能也能。更值得研究的是：你能不能调整它的工作方式，而且清楚地知道自己调整的是哪一层。

一个提示模板，可以帮你少复制一段话；一个 Skill，可以把某类任务的方法按需交给模型；一个 Extension，可以把可执行的行为接入 Pi。后面我们会用同一个验证任务，把这几层分开。现在先不要背名字。

另一个要记住的是：**界面上看起来都是一次对话，不等于背后没有状态。** 哪些内容送给模型、哪些只是留在历史里、工具现在能做什么、文件已经改成了什么，都影响下一步。我们稍后会专门拆“会话状态”和“工作目录状态”，因为混淆这两者，很容易在演示里踩坑。

最后，今天用的是 Pi 1.1.0 的资料和接口基线。社区文章有历史价值，但产品会变化。例如，早期文章里“不支持 MCP”的说法不能直接搬进今天的讲稿；本次基线已经有内建 MCP。我们会保留旧文章中有价值的工作方法，同时重新核对具体能力。〔证据：[O01](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o01)、[O14](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o14)、[C02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#c02)〕

**小检查，留 20 秒**

如果换了一个模型，`npm test` 的业务验收条件应该跟着变吗？

不应该。模型可以换，但我们对业务正确性的判断不该只依赖它怎么描述自己。这就是下一段演示的起点。

## 2｜12:00–20:00｜演示一：把“修好了”变成证据

> **操作细节在[配套演示手册](/Users/bloks/bzdev/playground/hello-pi/talk/demo-runbook.md)中。这里是台词和节奏，不临场安装、不临场登录。**  
> 演示目录必须是刚生成的可丢弃副本。不要在讲稿根目录启动模型，避免它读到参考答案。

### 12:00–13:00｜先让人看懂规则

**画面 04：五条任务。**

| 任务 | 状态 | archived | 应否计入 |
|---|---|---|---|
| T-101 | open | 缺省 | 是 |
| T-102 | in_progress | false | 是 |
| T-103 | done | 缺省 | 是 |
| T-104 | done | false | 是 |
| T-105 | done | true | 否 |

**讲稿**

先看产品规则，不看实现。只有 `archived: true` 被排除。没有这个字段，也属于未归档。这很像一个旧接口逐渐增加新字段的场景：新数据有显式标志，旧数据可能没有。

请大家先自己数一遍。我们应该得到四个任务：一个待办、一个进行中、两个已完成。这个数字由业务规则决定，不是由模型决定，也不是从待测实现反算出来。

### 13:00–14:00｜把红灯点亮

**操作**

```bash
npm test
npm run demo
```

**应该观察到**：五个测试中四个通过、一个失败；CLI 的实际错误输出是：

```json
{ "total": 2, "open": 0, "inProgress": 1, "done": 1 }
```

**讲稿**

我们先让错误自己出现。不是只说“这里有 bug”，而是让验收条件对当前实现产生一个明确的反例。现在，等会儿不管谁来改代码，都不能只靠解释过关。

这里不是给真实系统下结论的完整测试体系。我们只为这一个教学缺陷准备了一个足够小、足够清楚的验收边界。

### 14:00–17:00｜给 Pi 一个有边界的任务

**输入，不把参考修复贴给模型：**

```text
请修复当前任务统计错误。
先读 AGENTS.md、README.md、src/summary.ts 和 test/summary.test.mjs，并运行 npm test 复现。
遵循 README 的产品规则，只做必要的实现修改；不要更改测试或 fixtures，不增加依赖。
修改后再次运行 npm test 和 npm run demo。
最后报告：根因、具体改动、实际验证结果、尚未验证的边界。
不要读取当前演示目录以外的文件。
```

**讲稿**

大家注意，我没有告诉它把哪一个运算符换成哪一个。我提供的是任务、规则、改动边界和完成条件。

这四件事比一长串“你是一位资深专家”“请认真思考”更容易被检查。当然，这仍然是给模型的工作指令，不是操作系统级的访问控制。它不能代替隔离环境。今天的数据和目录本来就是专门准备的教学副本。

接下来请不要只盯它最后一句话。我们观察三个节点：是否真的运行了失败测试；它依据的是哪条规则；修改后有没有新的执行结果。能看到这些，才知道这次成功是怎么来的。

**讲者等候策略**

- 模型工作时，用最多 30 秒让观众指出“缺省字段”和“显式 false”为什么可能被区别对待。
- 等候超过 90 秒，不用聊天填满时间；直接启动手册中的参考修复兜底。
- **17:00 是修复等待硬截止。** 接下来的三分钟一定留给结果解释。

### 17:00–19:00｜看最小改动和结果

**参考修复；只有模型完成或切换兜底后才展示：**

```diff
- const active = tasks.filter((task) => task.archived === false);
+ const active = tasks.filter((task) => task.archived !== true);
```

**讲稿**

原代码只收下显式等于 `false` 的任务，把缺省字段的旧数据也排除了。修复以后，只排除明确归档的任务。这个改动对应了刚才那条业务规则。

现在我们重新跑测试，应该是五项通过、零失败；重新跑示例，应该是四、一、一、二。

我们还要看另一个问题：有没有通过改测试把红灯藏起来？有没有顺手增加依赖或者重写整个 CLI？小任务的好结果不只是“最后是绿的”，还包括改动范围与任务相称。

也请注意，这五项通过，只能说明这五个验收场景通过。它不自动证明所有非法输入都被处理了，不证明 TypeScript 静态检查通过，也不证明生产系统可以直接上线。教学代码明确没有做外部 JSON 的运行时 schema 校验。

### 19:00–20:00｜让观众说出发生了什么

**提问**：这次我们获得的，哪些是模型的陈述，哪些是工具执行的证据？

**收束台词**

到这里，Pi 不是靠“相信我”完成工作的。我们把任务放进了一个有反馈的循环：读规则、执行、看失败、修改、再执行。接下来要解决的是：任务变长、出现支线以后，怎样不把这个循环搅成一锅粥。

**兜底诚实台词**

“当前模型请求没有在时间窗内完成。接下来我切到人工准备的参考修复，现场运行同一套验证。这能证明示例与验证流程可运行，但不能证明刚才那次模型请求已经成功。”

## 3｜20:00–30:00｜上下文不是聊天记录堆得越多越好

### 20:00–23:00｜先分清两种状态

**画面 05：两个相互关联、但不能互相替代的状态。**

```text
会话 / 上下文                         工作目录 / 外部世界
--------------------------------    --------------------------------
人提出过什么问题                      summary.ts 已被修改
模型看见了什么文件与工具结果          测试产生了实际执行结果
当前沿着会话树的哪条路径继续          数据库或第三方服务可能已改变
压缩后保留了什么摘要                  Git / 文件系统决定文件如何恢复
```

**讲稿**

刚才的问题很小，整段讨论都围绕一个 bug。但真实开发经常不是这样。你修一个功能，中途发现测试工具不好用；修完测试工具，又开始讨论目录结构；然后有人要求顺便做一次安全审查。

最后你问模型“回到刚才的功能，下一步是什么”，它要在一大堆混在一起的材料里找方向。

这里先不要急着学某个命令。我们先区分两种状态：一边是会话和上下文，一边是工作目录和外部世界。

会话里记录“我们改过这个文件”，和文件真正被改了，是两件相关但不同的事。你回到一个早期的会话节点，不代表文件也自动退回那个时刻。**会话分支不是 Git 分支，也不是文件系统快照。**〔证据：[O04](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o04)〕

用刚才的例子说：我们已经把 `=== false` 改成了 `!== true`。如果这时切回修复之前的一条对话，文件依然可能是修复后的状态。新的上下文如果需要准确了解文件，就应该重新读取，而不是假定世界随着对话一起倒带。

这不是挑 Pi 的毛病，而是使用任何有工具的 agent 都需要建立的边界意识。只要工具能影响外部世界，聊天记录就不再是整个系统的全部状态。

### 23:00–26:00｜用会话树把支线放到合适的位置

**画面 06：教学示意，不是本机真实会话截图。**

```text
A 复现统计错误
└─ B 讨论最小修复
   ├─ C 应用修复并验证            ← 主任务
   └─ D 独立审查 archived 语义     ← 临时支线
      └─ E 发现旧数据缺字段是关键前提
```

Pi 的会话文件是带关联关系的 JSONL 条目，能够表达树，而不是只能一路向下追加的平面聊天。构造当前模型上下文时使用的是活动路径，分支摘要等机制可以把相关信息带回来；不是默认把所有兄弟分支的原文一起塞给模型。〔证据：[O04](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o04)〕

这提供了一种工作方式：主任务先留在这里，临时开一条线去审查边界或者研究一个工具，再把结论带回主线。

在 Pi 中，`/tree` 用于在当前会话的树中导航；`/fork` 创建独立的新会话文件。两者都不是“自动创建一个隔离的代码工作区”。本次我们只讲清意义，不在十分钟里连做两个导航演示。〔证据：[O04](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o04)〕

社区里，Armin Ronacher 分享过利用分支处理临时工具修复和审查的工作方式。这是作者自己的经验，不是“每次分支都会提高效果”的官方保证。我们能借鉴的是组织任务的方法：**让一条上下文尽量围绕一个清楚的问题。**〔证据：[C02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#c02)〕

举个回到本例的支线问题：如果接口传来 `archived: null`，应该算什么？这是一个值得问的问题，但它是否属于本次修复，要由产品约定决定，不由模型擅自扩大范围。

如果这只是研究支线，可以记一条结论：“当前练习输入保证 archived 为 boolean 或缺省；其他值不在本次验收范围。”这句话带回主线就够了，不一定需要把整段猜测和讨论带回来。

**互动 30 秒**

问听众：“为什么不能把新分支叫成‘干净、安全、独立的环境’？”

期待回答：它隔开的是讨论路径，不自动隔离磁盘文件、进程、账号和网络。

### 26:00–29:00｜压缩能缩短输入，不能保留所有细节

**画面 07：一份好摘要的例子。**

```text
目标：修复任务统计，避免缺省 archived 的旧数据被遗漏。
约束：只改实现；不改测试和样例；不增加依赖。
已验证：5 项测试通过；样例为 total=4/open=1/inProgress=1/done=2。
未覆盖：非法 status、archived:null、外部 JSON schema 验证。
下一步：审查差异；不要把演示通过当生产上线批准。
```

上下文变长以后，还会遇到压缩。可以把它理解为：后续请求不再反复携带所有旧细节，而是用摘要等内容保留继续工作所需的信息。Pi 的压缩不会因此删除会话文件里的原始历史，但原文仍在磁盘上，并不等于模型每一轮还在完整读取原文。〔证据：[O04](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o04)〕

所以有两个常见误解。一个是“压缩就是聊天记录没了”，另一个是“原始记录还在，所以模型没有丢任何信息”。这两句话都不准确。

对于我们的示例，一个有用的摘要应该保留目标、规则、实际验证和未覆盖边界。只写“已修复并验证，一切正常”，对下一轮帮助很小，也抹掉了我们最在意的证据范围。

这里有一条我建议团队采用的习惯：**任务切换或上下文收束时，优先保留决定下一步行为的事实。** 不需要写一篇漂亮的会议纪要，应该保留的是“已经知道什么”“还没有知道什么”“不能越过什么边界”。这是工作方法建议，不是 Pi 对摘要质量的保证。

### 29:00–30:00｜本段收束

这一段只带走三句话。会话是树，不必把所有支线混在一条对话里。树的切换不等于文件回滚。压缩保留继续工作的摘要，但需要我们关注哪些关键事实可能被省略。

**转场**

到现在，我们还是在用文字提醒模型。下面看，当某条提醒开始重复时，应该怎样逐步固化，而不是第一天就写一个大插件。

## 4｜30:00–38:00｜提示、Skill、Extension：不要把它们都叫“插件”

### 30:00–32:00｜从一句重复提醒开始

**画面 08：把同一个需求放到三层。**

```text
重复的话：审查这次改动，给出依据与未验证项。         → Prompt Template
重复的方法：按产品规则复现、修复、验证、报告。        → Skill
重复的动作：执行指定测试并显示实际结果。              → Extension
把这些资源发给其他人。                              → Package
```

**讲稿**

我们回到刚才的任务。假设我下次修另一个 bug，仍然要提醒：“读规则，先复现，修改后跑测试，不要把没做过的验证写成做过。”

第一次直接说很合理。后来你发现总在重复，就可以按需求的性质逐步固化。但不要把所有东西都叫插件，因为这会遮住一个非常重要的区别：有些内容是在指导模型，有些代码是在实际执行。

第一层是 Prompt Template，也就是提示模板。它很适合保存一段反复输入的话。在 Pi 中可以用 Markdown 定义模板，用命令展开，并把参数放进提示里。它节省的是重复输入和表述不一致。〔证据：[O06](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o06)〕

比如我们准备了一个 `review.md`：要求依据产品规则审查当前实现，区分观察到的证据和未验证项。输入 `/review` 时，发生的是提示展开，**不是一个叫 review 的独立程序开始执行静态分析**。

第二层是 Skill。它更像某一类任务的方法包：一个 `SKILL.md` 可以带着脚本、参考资料和其他文件。Pi 启动时会把可用 Skill 的名称、描述和位置提供给模型，完整说明按需读取；也可以通过 `/skill:name` 明确加载。〔证据：[O07](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o07)〕

关键不是“文件名叫 SKILL.md 就神奇了”，而是把何时使用、怎么做、完成条件和必要参考组织清楚。描述写得太泛，例如“帮助开发”，模型很难知道什么时候该找它。明确写“修复这个教学项目后，按测试和样例输出核验再报告”，适用范围就清楚得多。

### 32:00–35:00｜看一份短 Skill，而不是背规范

**画面 09：教学资源中的核心步骤。**

```markdown
1. 读取 README，恢复产品规则。
2. 运行 npm test；失败就报告失败，不宣布完成。
3. 运行 npm run demo，对照 README 里的字面预期值。
4. 报告实际结果和未验证边界。
```

这段内容很短，因为它只处理一件事。它不是一本包含整个公司的研发制度手册。团队真正长期使用时，可以把只在某个分支才需要的材料放到参考文件，避免每次处理小问题都读取一大堆无关说明。

但要保持清醒：**方法说明不是强制执行器。** Skill 可以指导模型去跑测试，模型仍可能漏做，或者误解结果。不能因为“仓库里有一个 Skill”，就说这个仓库有了可靠的测试门禁。

这时才来到第三层：Extension。Pi 的 Extension 是运行时加载的 TypeScript 或 JavaScript 模块，可以注册命令、工具或事件处理等能力。我们今天不把这些接口全部讲一遍，只做一个用户明确触发的命令 `/verify`。〔证据：[O08](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o08)〕

这个命令做一件很具体的事：启动我们预定的测试程序，读取真实退出结果，把结果显示出来，并记录到会话中。它不需要让模型先判断“我想不想跑测试”。

这并不意味着 Extension 比 Skill 更高级，应该一律替代 Skill。它们解决的不是同一个问题。业务判断、解释规则、理解代码，仍然需要模型或人参与。固定动作可以用代码做好，方法知识仍然适合通过文字交给模型。

### 35:00–37:00｜一张选型表，停止过度设计

| 需求 | 优先考虑 | 不能误以为 |
|---|---|---|
| 少复制一段审查提示 | Prompt Template | 自动执行了审查程序 |
| 复用一类任务的方法与资料 | Skill | 形成不可绕过的安全或流程门禁 |
| 提供可执行命令、工具、事件处理 | Extension | 不用审查就能安全运行 |
| 打包、分发上述资源 | Package | 一个新的隔离或权限层 |

Package 的意义是分发。你可以把扩展、技能、提示和主题放在一个包里，减少每个人手动拷文件。但分发形式不会自动让内部代码可信。装进 npm 包里的危险动作，依然是危险动作。〔证据：[O09](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o09)、[O13](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o13)〕

我的建议是按最小需要升级：一句话能讲清就先用一句话；重复到值得固化再做模板；知识和步骤变多再做 Skill；确实需要执行入口或运行时接入，再做 Extension。不要先建一个宏大的插件平台，再回头寻找需要它的工作。

### 37:00–38:00｜转场小检查

现在我说：“我们增加了 `/verify`，因此模型再也不可能在没跑测试时宣称完成。”这句话对吗？

不对。我们新增的是一个明确、可观察的执行入口。除非另行做了相应的控制，它并没有变成不可绕过的门禁，更没有替代 CI。接下来我们就看这个命令实际做到了什么，没有做到什么。

## 5｜38:00–45:00｜演示二：一个小扩展，固定动作，暴露证据

### 38:00–39:30｜只读核心，不从空文件写起

**画面 10：以下是从完整文件裁剪的讲解片段，不可单独粘贴当完整扩展。**

```ts
pi.registerCommand("verify", {
  description: "Run this workshop's five tests and record the actual result",
  handler: async (_args, ctx) => {
    // 完整文件另含：空闲检查、项目范围检查、超时和异常处理。
    const result = await pi.exec("node", [
      "--disable-warning=ExperimentalWarning", "--test", "test/summary.test.mjs",
    ], { cwd: ctx.cwd, timeout: 15_000 });
    const passed = result.code === 0 && !result.killed;
    // 完整文件把输出显示并记录到会话，triggerTurn: false。
  },
});
```

**讲稿**

我们不现场从空文件写扩展。大家先看三个点就够了。

第一，注册的是 command，所以是人输入 `/verify` 时触发。它不是供模型选择调用的 tool；如果需要后者，要使用相应的工具注册接口，不能只改一个名字。

第二，它通过 Pi 的执行接口启动真实的 Node 测试进程。固定参数传给进程，不把用户输入拼成一条 shell 字符串。完整代码还检查演示目录和超时，但这些检查也不是操作系统沙箱。

第三，成功判断同时检查退出码和是否被停止。我们不让“被超时中断的进程”因为某种返回形式被展示成成功。结果和一段实际输出会进入会话，但命令本身不自动触发新一轮模型请求。〔证据：[O08](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o08)、[L01](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#l01)〕

### 39:30–41:00｜加载并调用

**操作**

1. 将预先审阅的资源复制到演示副本；按手册重新启动同一目录中的 Pi，并显式加载扩展。
2. 输入 `/verify`。
3. 展示 `verify: PASS`、退出码和测试统计，而不是只指一下绿色状态。

**讲稿**

现在我们输入 `/verify`。真正有价值的不是又多了一个斜杠命令，而是几件事情一致了：在哪里运行、运行什么、什么时候算通过、结果在哪里看。

如果你和另一位同事都使用同一份已审阅的扩展，在同一份代码上执行，它会运行同一个测试入口。当然，依赖、环境和代码内容仍然会影响结果，所以我们仍要记录版本和环境。

这里的反馈也不需要模型替我们“评价一下看上去通过没有”。程序根据退出结果直接展示。这是把确定性的部分交给代码，不是试图让模型取代所有确定性逻辑。

### 41:00–42:30｜验证失败路径，而不是只看 happy path

**画面 11：展示离线接口验证记录，明确不是交互 TUI 录像。**

```text
未修复副本：verify: FAIL; exit=1; stopped=false
已修复副本：verify: PASS; exit=0; stopped=false
```

**讲稿**

我还提前验证了失败路径。这里的记录来自本机 Pi 1.1.0 的真实扩展加载器和命令执行接口，但没有调用模型，也不是一段 TUI 录像。

为什么要特意说清楚？因为“接口测试通过”“界面能正确操作”“模型在现场稳定完成任务”，是三种不同程度的验证。我们应该像要求模型一样要求自己，不把没做的那一步说成已经做了。

初始副本会被这个命令判成失败，修复副本判成成功。它不会因为结果文字里面出现一次“pass”，就忽略另一个失败。

### 42:30–44:00｜可选展示一次 reload，保留硬截止

**操作**：在演示副本的扩展里，只把成功通知文字加上 `demo checked`，执行 `/reload` 后再输入 `/verify`。若启动或界面状态不稳定，跳过，不现场调试。

**讲稿**

Pi 支持重新加载扩展。对这种小型、自己维护的工作流入口来说，修改和再验证的反馈比较直接。但是 reload 的存在不意味着随便改权限、随便加载别人代码都安全。项目资源是否受信任，以及代码实际会做什么，仍然要审查。〔证据：[O08](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o08)、[O13](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o13)〕

在团队里，这种能力最适合从一个小地方开始：把已有、经过验证的命令接进来，而不是把业务逻辑、任务数据库和执行平台全部重写到一个扩展里。

### 44:00–45:00｜本段必须讲出的限制

请一定记住两点。`/verify` **不自动拦截之后的提交或发布**。它也不会因为测试曾经通过，就保证代码后来又修改过仍然通过。

所以它提供的是一个低摩擦的验证入口和一份可见证据；真正不可绕过的要求，要在合适的位置落实，例如受保护的 CI 检查、受限凭据和明确的发布权限。后半句是我们的工程建议，不是这个示例扩展已经实现的功能。

**转场**

现在我们把一条本地动作接进来了。接下来用十分钟看：如果要连接更多团队工具，怎样不把这个简单系统变成难以理解的黑箱。

## 6｜45:00–55:00｜接入更多工具之前，先问清楚接口和边界

### 45:00–48:00｜同样叫“接入”，其实有几个方向

**画面 12：以调用方向理解接口。**

```text
在 Pi 内定制行为         → Extension
让 Pi 使用外部工具       → MCP
在 Node/Bun 程序内嵌入 Pi → SDK
用另一个进程驱动 Pi      → RPC
构建长运行、可恢复应用   → 下一节再讲 Durable
```

**讲稿**

到了团队场景，大家通常会问：能接内部任务系统吗？能放到我们的服务里吗？能不能用自己的界面操作？这些问题听起来都叫接入，但调用方向不同。

Extension 是在 Pi 里扩展行为。刚才的 `/verify` 就是这一种。

MCP 是让 Pi 连接外部工具和资源的一种接入方式。当前基线已经内建 MCP 支持，文档列出的传输包括 stdio 和 streamable HTTP，不支持旧式 SSE。MCP 也不是 RPC 的另一个名字。〔证据：[O10](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o10)〕

SDK 适合在 Node 或 Bun 程序内创建、驱动 Pi 会话。RPC 则把 Pi 作为一个独立子进程，通过 stdin/stdout 的 JSONL 协议控制它。一个是在进程内调用，一个是进程间协议，这会影响部署、生命周期和错误处理方式。〔证据：[O12](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o12)〕

这里再提醒一个不显眼的差别：不要假定 CLI 里自动有的资源，SDK 里默认就完全同配。当前 SDK 的内建扩展加载需要按文档明确配置；如果你要用 MCP/Codemode，更要检查资源加载设置。〔证据：[O12](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o12)、[O10](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o10)〕

我们今天不现场同时搭四套集成。选择接口之前，先写清楚一句话：“到底是谁在调用谁，需要控制什么？”这一句通常比比较一大张参数表更能缩小问题。

### 48:00–50:00｜用一份工具返回值解释 Codemode

**画面 13：不是真实 MCP 返回，而是教学输入示意。**

```text
任务工具：返回 100 条任务，带标题、描述、评论、负责人、状态……
验证工具：返回各任务最近一次检查结果和完整日志……
人的问题：只列未完成且最近检查失败的任务编号与一句原因。
```

如果把所有原始内容都交给模型，再让它从中挑出三条，模型就要看到很多与回答无关的材料。有时这些材料还包含你并不希望传播的信息。

Codemode 提供一种工具编排方式：可以在受限 JavaScript 解释器里组合调用工具、处理结果，再把需要的结果返回。这里我用的是说明思路的伪代码，不是可以直接复制运行的 Pi API。〔证据：[O11](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o11)〕

```text
并行读取任务与验证状态
→ 按任务编号关联
→ 过滤“未完成 且 最近检查失败”
→ 仅返回 {任务编号, 一句原因}
```

它的价值不是“写了代码就一定更省 token”，更不是“所有步骤都能偷偷并行”。你要看实际返回了什么、任务是否相互独立、失败时怎么报告。我们在这里能明确表达的是数据策略：**先做必要的选择和聚合，再把结果交给后续推理。** 不给未经测量的性能数字。

边界也要讲清楚：解释器不能直接使用 Node、文件系统和网络 API，并不意味着它调用的工具没有真实权限。工具如果能发通知，它就仍然能产生外部影响；执行中途失败，也不会自动撤销前面已经发生的副作用。〔证据：[O11](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o11)、[O13](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o13)〕

### 50:00–52:30｜三条社区经验，各带一条代价

**画面 14：不推荐“必装十个插件”，只提取可复用的方法。**

| 一手实践 | 我们借鉴的方法 | 必须保留的代价或限制 |
|---|---|---|
| Armin：分支处理工具修复、审查；`/answer` 收集回答 | 临时支线不要吞掉主任务，需求澄清做成可用界面 | 摘要可能遗漏；`/answer` 是扩展且会额外调用模型 |
| Julian Prokay：独立 `pic` CLI + 薄的 Pi `/task` 界面 | 数据和业务规则先有独立入口，Pi 做适配 | 仍需维护 CLI、数据格式、适配层 |
| Colin Jermain：`pi-less-yolo` 的容器与挂载实践 | 在环境层约束损害范围，不只在提示里要求小心 | 容器配置、挂载、网络和持久化配置仍可能带来风险 |

**讲稿**

社区经验里，我最建议带走的不是插件名称，而是作者为什么这么组织。

第一条是把临时问题放进支线，把结论带回来。我们刚才已经用过这个思路。Armin 还做了 `/answer` 一类交互扩展，帮助把自然语言问题转成易于回答的界面。但源码显示它会额外调用模型，所以要考虑延迟、调用成本以及问题提取是否正确；它不是 Pi 的内置命令。〔证据：[C02](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#c02)〕

第二条是先做独立 CLI，再接薄的一层 Pi 界面。Julian 的实践是把任务数据放在独立的 CLI 中，Pi 负责展示和交互。对已经有内部工具的团队，这个思路值得借鉴：先让核心能力在普通终端就能运行、测试和排错，再决定怎么让 agent 使用它。不要把所有业务知识塞进一个只能从聊天界面触发的扩展。〔证据：[C03](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#c03)〕

第三条是隔离误操作影响。Colin 的文章和仓库讨论了容器、挂载及只读模式，也明确保留了风险说明。我们引用它，不是推荐未经审阅直接安装，更不是说 Docker 三个字就解决了所有安全问题。我们借鉴的是把边界落实到环境配置的思路。〔证据：[C04](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#c04)〕

这些都是作者自己的实践，不是跨团队对照实验，也不能直接推出某个收益比例。适用场景、维护成本和版本兼容性都需要我们自己验证。

### 52:30–55:00｜安全边界用三个反例讲清楚

**画面 15：三句话判真假。**

```text
“我信任这个项目，所以 bash 被限制在这个目录里。”      错
“这个目录只读，所以所有外部风险都没有了。”             错
“Codemode 有沙箱，所以它调用的所有工具都没有副作用。”   错
```

Pi 的项目信任用于控制项目资源加载，不是操作系统沙箱，也不是默认的逐工具批准制度。当前官方安全文档明确要求理解实际进程权限与资源来源。没有被某种工具选择或提示暴露出来的入口，也不能据此宣称整个进程已经没有那些权限。〔证据：[O13](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o13)〕

拒绝项目信任也不等于这个目录里的所有文字都彻底不被读取；例如部分上下文仍会按文档规则加载。因此我们不能把一个“信任”开关解释成整个系统的唯一安全边界。〔证据：[O13](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o13)〕

对团队落地，我建议把检查拆成三张清单。第一，数据：这次任务会把什么发给模型，是否允许这样发。第二，执行：进程、工具、扩展到底能接触哪些文件和服务。第三，发布：哪些动作会产生不可轻易恢复的副作用，需要在哪个真实系统里做权限与审批。

具体到今天的演示，我们用的是无敏感数据的副本、固定的测试入口和人工审阅的扩展。我们还明确没有验证真实账号、MCP 服务或 Durable 运行。这些说明不是扫兴，而是让别人知道结论可以被复用到哪里，不能被复用到哪里。

**转场**

最后一种边界，比“有没有权限执行”再往前一步：假设动作已经执行了，但程序没来得及记住它执行过。这正好进入 Durable。

## 7｜55:00–60:00｜Pi Durable：进程能恢复，不等于通知可以随便重发

**画面 16：一个有明确外部副作用的任务。**

```text
读 issue → 生成处理草稿 → 给团队发通知 → 记录完成
                                  ↑
                         通知已发出，进程在记录前中断
```

**讲稿**

先换一个场景。我们不再坐在终端前等一个小 bug 修好，而是要运行一个长期存在的 agent 应用。它读取 issue，整理处理建议，然后给团队发通知。

假定调用意图已被持久化。流程跑到这里：通知已经被外部服务接收，但我们的进程在写入“已完成”的记录之前中断了。现在重启，你会做什么？

**停顿 20 秒，让大家先说“再发一次”或“查一下”。**

如果直接从头重跑，可能重复发消息。如果直接跳过，又可能在通知其实没有送达的另一种故障情况下丢掉通知。难点不在于重新启动那个进程，而在于恢复时，你对外部世界究竟知道多少。

2026 年 10 月 1 日的官方文章介绍了 Pi Durable。它是面向长运行 agent 应用的实验性框架，不是终端 coding agent 的改名，也不是让所有 Pi 会话自动具有同样保证的一个开关。文章明确提醒 API 仍可能变化。〔证据：[O15](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o15)〕

可以从三件事理解它的方向：保存继续工作所需的状态；中断后恢复任务；区分哪些工具调用可以安全重放。这里不讲未经运行验证的 SDK 方法名，我们只讨论官方设计所面对的问题。

工具是否可安全重放，需要开发者声明，框架不会替你证明它幂等。针对这里“调用意图已落盘”的中断，只有前后声明都满足安全重放条件才重跑；默认不安全的调用会返回中断信息。即使这一次没有自动重放，也不能阻止后续模型或人又发起一次新调用。**这不是替业务自动证明“那条通知到底有没有发出去”。**〔证据：[O15](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o15)、[O17](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o17)〕

**画面 17：把三个问题分开。**

| 问题 | 对应关注点 |
|---|---|
| 进程重启后还能找到原来的任务吗？ | 状态持久化与恢复 |
| 同一 conversation 的相同提交请求重试怎么办？ | 提交去重；例如 requestId 的约束范围 |
| 外部通知已发送，但本地未确认，能否再发？ | 工具副作用、查询核对、幂等设计 |

尤其要小心 exactly-once 这个词。`requestId` 在同一 conversation 内用于取回原提交，并不是任意外部工具的副作用保证；不同业务请求不能随意复用同一个 ID。提交任务没有重复，不代表外部通知或写操作也自动只发生一次。〔证据：[O16](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o16)、[O18](/Users/bloks/bzdev/playground/hello-pi/research/source-register.md#o18)〕

对于通知场景，我们通常还需要自己的业务设计：为动作分配稳定标识，核对服务端状态，使用外部系统真正提供的幂等能力，必要时交给人判断。这里是工程建议，不是说 Durable 已经替我们实现了这些外部系统的保证。

所以今天对 Durable 的结论很克制：当你有跨进程存活、较长生命周期、需要恢复的应用需求时，它值得进一步研究；如果你现在只想把个人终端里的验证工作流做好，先把前面的上下文、工具和验收做好，不需要因为看见 durable 这个词就把架构升级一遍。

**转场**

我们从一个很小的统计 bug 走到了长运行任务。最后五分钟，把这些内容压回下周能做的一件具体事。

## 8｜60:00–65:00｜收束：别先做平台，先复现一条工作流

**画面 18：同一个案例走过的路径。**

```text
产品规则
  ↓
失败证据 → Pi 的模型 / 工具循环 → 最小修复 → 验证结果
                         ↓
              用会话与摘要管理支线
                         ↓
             用合适的层次固化重复部分
                         ↓
             给执行权限与外部副作用划边界
```

**讲稿**

今天我们没有接十个服务，也没有做一个“能自主完成所有研发任务”的系统。我们只把一条小工作流尽量走清楚了。

开始时，错误只是一个统计数字。我们先把产品规则写清楚，建立一个失败证据，再观察模型和工具如何一起工作。修复以后，我们没有停在“好了”，而是看测试和实际输出。

然后我们看见，任务一旦变长，就需要管理上下文：支线可以分开，结论可以带回来，但会话不替文件回滚。重复的方法可以做成模板或 Skill；固定的动作可以接成 Extension；这些东西可以打包分发，但打包不等于安全。

最后，我们把边界带到更大系统里：MCP、SDK、RPC 不是互相替代的名字，应该按调用方向选择；解释器沙箱不等于工具无权限；能够恢复任务，也不等于副作用可以随意重试。

如果大家回去只记一个工作原则，我希望是：**把需要判断的部分交给判断，把能确定执行的部分交给代码，把“做没做、做成什么”留成证据。**

**画面 19：建议的一周试点，不是产品效果保证。**

1. 选一个低风险、验收条件清楚、每天或每周会重复的任务。
2. 用现有方式做一次，记录步骤、耗时和人工检查点。
3. 用 Pi 做同一类任务，保留提示、必要日志、实际结果和人工接管点。
4. 只固化真正重复的一小段；先不建设通用平台。
5. 对照失败率、返工、审查成本和权限风险，决定是否继续。

这里的重点不是追求一个漂亮的平均耗时数字。一次任务看起来更快，但如果增加了很多人工排查和复核，也可能并不值得。反过来，如果某个小扩展只是稳定地减少漏跑测试，价值也可能足够清楚。我们需要的是能对比的记录，不是演示现场的兴奋感。

对今天的示例，听完以后你应该能够独立做三个动作：把初始错误复现出来，解释参考修复为什么对应规则，运行 `/verify` 并指出它没有替你保证什么。完成这三个动作，比记住所有斜杠命令更重要。

**最后三个问题，邀请全场快速回答。**

- 模型说测试通过，与工具实际执行通过，是同一件事吗？——不是，要看证据。
- 切换会话分支后，文件自动回到原来的版本吗？——不能这样假定。
- 有了 `/verify`，就有不可绕过的上线门禁了吗？——没有，它只是一个明确的验证入口。

如果这三个问题已经清楚，今天最重要的目标就达到了。

接下来十分钟问答。欢迎带具体场景来问：你想让谁调用谁、现在哪里最容易漏步骤、哪些数据不能离开环境、哪些操作不允许重复。我们尽量从这些约束出发，而不是继续堆一页新名词。
